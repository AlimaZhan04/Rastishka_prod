# РАСтишка — минимальный процесс разработки

## Перед началом задачи

1. Найти строку или строки `FR-*` в `docs/MVP_REQUIREMENTS_TRACKER.md`.
2. Проверить зависимые открытые вопросы в `docs/DECISIONS_AND_OPEN_QUESTIONS.md`.
3. Создать короткоживущую ветку `codex/<module>-<short-name>`.
4. Сформулировать критерий приёмки до начала реализации.

## Pull request

Каждый PR должен содержать:

- идентификаторы `FR-*`;
- краткое описание пользовательского сценария;
- список изменённых миграций и переменных окружения, если они есть;
- способ проверки и ссылку на тесты;
- скриншоты desktop/mobile для публичных интерфейсов;
- план отката для изменений схемы БД или внешних интеграций.

## Обязательные проверки

Перед слиянием запускаются:

```powershell
pnpm typecheck
pnpm lint
pnpm build
```

После добавления тестового раннера также обязательны релевантные unit, integration и E2E-тесты. P0 нельзя закрыть только ручным просмотром компонента: нужен полный сценарий, включая сервер и БД, если требование их затрагивает.

## Работа с данными и миграциями

- Изменения `prisma/schema.prisma` сопровождаются миграцией, проверенной на staging.
- Секреты, реальные телефоны, ключи API и файлы резюме не попадают в Git, логи или тестовые фикстуры.
- Операции с ПДн должны быть минимально необходимыми; ошибки и уведомления не раскрывают чувствительные данные ребёнка.

## Обновление трекера

- `Запланировано` → `В работе` при старте задачи.
- `На проверке` — когда PR готов и есть доказательство критерия приёмки.
- `Готово` — только после слияния, успешной проверки и обновления ссылок `PR` и `Тест`.
- Если внешняя зависимость мешает выполнению, использовать `Заблокировано` с причиной в заметке PR или в реестре решений.
